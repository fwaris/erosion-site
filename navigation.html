    Navigation and effects¶

    Imagine editing a task on a phone. You expect Back to return you to the same filtered list. You might also expect Back to throw away the title you just typed. Both behaviors come from where the app stores those two values. The Projects exhibit lets you try them side by side. In Live monitor, leaving the screen also stops a worker that has been sending it fresh prices.

    Push and pop a page¶

    Gallery keeps its search text in the app model and its page stack in Routes<Page>. Search for “slider,” open the matching exhibit, then go back. The catalog still shows the same search because both pages use the same app instance.

    To add a destination, give it a variant in your app’s Page enum. A button can bind to Msg::Open(Page::Detail). Handle that message in DeclarativeApp::update by calling self.nav.push(page). In view, match on self.nav.current() to choose the content. The navigation hook passes the stack to Erosion:

    fn navigation(&self) -> Navigation {
    self.nav.navigation()
}

    Handle system Back in on_host_event with self.nav.pop(). Use present(page) for a sheet or push_with_transition(page, Transition::Fade) for a fade. Field Catch also calls handle_root_back() on the returned navigation value so it can leave AR or end a session from the root page.

    Erosion gives each visit its own internal ID. If a late tap arrives from the first visit to Detail after a second visit has opened, the runtime discards it. The app just works with Page::Detail. A device reply has a different lifetime: a save that belongs to a document may still matter after the editor closes.

    Give each section its own model¶

    Open Controls Gallery → Projects. Filter the list to “garden” and open the first project. Its editor starts with a copy of the saved task. Back drops the draft. Save copies the edited title into the Gallery’s records before popping the editor. Back from the detail page reveals the original filter. Leave Projects entirely and the next visit starts with an empty filter.

    The application still has one root model. Its route stack owns just the pages the user has opened. A page can carry ordinary Rust values. For example:

    enum ProjectsPage {
    List { filter: String },
    Detail(usize),
    Editor { project: usize, draft: String },
}

    At the moment the editor opens, three pages are on the Projects stack. Here’s what each one owns and when the user will see that value again.

    Value Where Gallery keeps it What happens on Back
    “garden” in the filter field The list page Opening a project covers the list. Returning to it reveals the same filter. Leaving Projects drops it.
    The title being typed The editor page Closing the editor drops its draft. Opening another editor makes a fresh copy of the saved title.
    The saved task title The Gallery’s project records Save updates the record before popping the editor. The detail page then renders the new title. It lasts for this app session.

    A large app can follow the same pattern one section at a time. Borrow the active page with nav.current() to render it and nav.current_mut() to edit it. Popping a page drops the Rust values it owns. Falling Blocks allocates its board when the player starts a game. Its Play page owns the board through a Box, so returning to the lobby releases the board while the app keeps the high score. To keep a value through process exit, save it separately. Falling Blocks writes the high score to a file.

    Projects also has its own messages. In samples/gallery/src/projects.rs, the editor binds the Save button to the section’s Msg::Save. The Gallery wraps the whole screen with .map_msg(Msg::Projects). A tap then reaches the Gallery as a Projects message, and the Gallery passes it to the section’s update function. This lets someone editing the task feature find its fields, buttons, and rules together.

    Receive messages from background work¶

    Open Controls Gallery → Live monitor and leave the phone untouched. Once a second, a Rust worker generates prices for three fictional stocks. When a batch arrives, the prices and the received-batch count change together. This example runs offline.

    A button press already arrives on the phone’s UI thread. The quote worker runs on another thread, and the phone may be idle when its next batch is ready. Erosion supplies an AppSender<Self::Msg> in the app’s on_attach hook. The app gives the worker a clone. Sending a message wakes the native UI loop, which delivers the message to the same update method that handles the Pause button. The worker can finish its job without touching a native control or locking the dashboard model.

    Here’s the sending end from samples/gallery/src/monitor.rs. It runs inside the worker’s loop:

    match sender.try_send(Msg::QuoteBatch(run, quotes)) {
    Ok(()) | Err(TrySendError::Full(_)) => {}
    Err(TrySendError::Closed(_)) => break,
}

    A successful send puts the batch in a bounded queue. If the queue fills, the monitor skips that batch because another price will arrive shortly. An app sending an edit that must be saved would need a different policy. Both error variants return the original message so the producer can keep it. A closed sender means its host attachment has ended and this worker can exit. The example uses a standard Rust thread. An app that already uses Tokio can give the same sender to one of its tasks.

    Pause, leave, and come back¶

    Tap Pause feed. The prices stay on screen because the route still owns the dashboard model. The app drops a separate cancellation handle, which wakes the worker and ends its loop. Resume starts another worker from the displayed prices. Putting the app in the background also stops the feed. On returning, a paused dashboard stays paused. Back closes the route altogether, so the next visit starts at zero batches.

    There’s a small race worth testing in your own app. A worker could queue one last batch just before the user taps Pause. By the time the phone delivers it, the user may already have tapped Resume. Live monitor gives each run an ID and checks it in Dashboard::receive. Only a batch from the current run can change the displayed prices. If the native host is recreated, Erosion closes the old sender before calling on_detach. The next on_attach supplies a fresh sender.

    Request a native operation¶

    The app queues effects and drains them in effects(). Assign a fresh request ID for each operation and store it with the domain data that will receive the result. A save can update an item while its editor is closed. Reopening the editor renders the saved value. If leaving should abandon an operation, clear the pending request in update and issue Effect::CancelCapability { id } to stop the native work.

    use erosion_ui::{capabilities::Operation, runtime::Effect};
let request = Effect::Capability { id: 42, request: Operation::PickPhoto };

    On HostEvent::CapabilityResult, match the ID before applying the outcome. An Outcome::Asset contains a private asset reference that can be persisted with the note. Handle cancellations and permission denial explicitly. The device guide lists operations and sample setup.

    Deep links and local notifications¶

    An app can assign a stable note ID when saving and open links such as mrust-notes://note/2. Schedule a local notification with Effect::ScheduleReminder { id, title, url, delay_seconds }. Handle HostEvent::OpenUrl { url } in Rust so tapping the reminder routes to the same saved note as opening the link. Register the URL scheme when packaging a new app. Android may defer delivery when exact alarms are unavailable.
