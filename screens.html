    Screens and state¶

    A generated app supplies a model, an update function, and a view. Erosion turns the view into native controls and delivers their bound messages to the app. For direct control of rendering and event dispatch, an app can implement runtime::Application.

    Model, message, and update¶

    Use this optional pattern when several controls or events can change the same state. The model holds the current state. A message (Msg) names an intent. Update applies that intent to the model, and the view describes the screen from the resulting state.

    use erosion_ui::{declarative::{button, strata_screen, text, ViewScreen}, design::Role, view};

#[derive(Default)]
struct Model {
    count: u32,
}

#[derive(Clone)]
enum Msg {
    Increment,
}

fn update(model: &Model, msg: Msg) -> Model {
    match msg {
        Msg::Increment => Model { count: model.count.saturating_add(1) },
    }
}

fn counter(model: &Model) -> ViewScreen<Msg> {
    view! {
        strata_screen(0, "Counter") {
            text("count", model.count.to_string(), Role::Body);
            button("add", "Add one").on_press(Msg::Increment);
        }
    }
}

erosion_ui::erosion_app!(Model::default, update, counter);

    The single-screen adapter uses route zero and keeps one set of mounted bindings per app instance. To handle lifecycle, Back, or device replies, implement app::DeclarativeApp with your own message type. Its update receives bound messages and its on_host_event receives unbound HostEvent values. Return Box::new(AppAdapter::new(app)) from the native factory. Override the route and presentation hooks when your model owns a navigation stack.

    How the games use it¶

    • Falling Blocks binds the Left button to Msg::Move(Move::Left). A left swipe is classified as Move::Left and reaches the same Game::apply_move rule. The game owns its board, score, and phase. The application adapter handles clock ticks, navigation, and saving the high score. Start with samples/falling-blocks/src/view.rs and follow the binding into src/lib.rs.
    • Field Catch binds both keyboard submission and the Join Field button to Msg::JoinField. Its reducer takes an AppInput, which can carry a UI message, a typed WebRTC callback, or another platform event. It returns the next model and effects for the host to execute, such as requesting GPS. Start with samples/field-catch/src/view.rs and follow AppInput and update in src/lib.rs. Navigation and effects

    Compose the view¶

    A child block accepts immutable let bindings, if let, if/else, match with braced arms, and for. End leaf and component expressions with a semicolon. Return a ViewNode<Msg> for one control or a Fragment<Msg> for several siblings. A fragment adds no native container. Use item-derived keys in loops and give every interactive source a unique key across the whole screen, including toolbar and accessibility actions.

    Use a toolbar { ... } block on the screen root. For example, a call action can be declared as toolbar_item("video-call", "Video call", "video_camera").enabled(can_call).on_press(Msg::VideoCall);. Toolbar conditions follow the same rules as body conditions. Import widgets::ViewModifiers for style methods such as .rounded(12). An existing keyed Node can be inserted directly. Wrap it with from_node to attach a typed native event binding. The complete example lives in samples/field-catch/src/view.rs.

    Build a keyed editor¶

    use erosion_ui::{
    widgets::{button, column, field, ViewModifiers},
    Node,
};

fn editor(title: &str) -> Node {
    column("editor", vec![
        field("title", "Note title", title),
        button("save", "Save note").rounded(12),
    ])
}

    Place editor(&self.title) in the children passed to widgets::screen. Give each sibling a unique, stable key. A key describes a control’s identity across renders. Changing it can replace the native field and interrupt an edit.

    Handle native input¶

    In an existing app model with a title: String field and a save() method, the update branches for the editor look like this:

    match event {
    HostEvent::Input { key, value } if key == "title" => self.title = value,
    HostEvent::Press { key } if key == "save" => self.save(),
    _ => {}
}

    For a Control::List, give every Item its own persistent numeric ID. Handle HostEvent::Pick { key, id } using that ID, so filtering or reordering rows still opens the correct item.

    Choose an authoring style¶

    Widget functions and chainable modifiers cover common controls. Use Control variants directly for more specialized declarations. The optional ui! macro constructs the same keyed nodes:

    use erosion_ui::{ui, widgets::button};
let form = ui!("form" => Column [
    ui!("volume" => Slider { label: "Volume".into(), value: 35 }),
    button("save", "Save"),
]);

    The engine compares successive screen descriptions and sends changes over a revisioned bridge. The declarative API, individual widget constructors and both macros use that update path.

    Register a separate app¶

    Add a crate under samples/, list it in the workspace, and depend on erosion-ui by path. Implement Application and export its factory with erosion_native_host::export_app!. Add the corresponding Android module in android/mobile/build.gradle and a dedicated XcodeGen project under ios/ (for example, ios/Gallery.yml). Use the same app selector for both hosts. After this initial setup, ordinary screens can be added entirely within the Rust crate.
