    Screens and state¶

    Open src/lib.rs in a generated app. Everything you need to change the counter is in that file, including its test. The same Rust view runs on both phones. Erosion creates the native buttons and labels and keeps them in sync with the model.

    Model, message, and update¶

    Follow Increment through the starter. The button binds a press to Msg::Increment. The app decides what that message does in update. When view reads the new count, Erosion compares the screen with the previous one and sends the changed label to the host.

    use erosion_ui::{
    declarative::{button, strata_screen, text, ViewScreen},
    design::Role,
    erosion_app,
    view,
};

#[derive(Default)]
struct Model {
    count: u64,
}

#[derive(Clone)]
enum Msg {
    Increment,
}

fn update(model: &Model, msg: Msg) -> Model {
    match msg {
        Msg::Increment => Model {
            count: model.count.saturating_add(1),
        },
    }
}

fn view(model: &Model) -> ViewScreen<Msg> {
    view! {
        strata_screen(include_str!("../app-name.txt")) {
            text("count", format!("Count: {}", model.count), Role::Title);
            button("increment", "Increment").on_press(Msg::Increment);
        }
    }
}

erosion_app!(Model::default, update, view);

#[cfg(test)]
mod tests {
    use super::*;
    #[test]
    fn increment_updates_count() {
        let model = update(&Model::default(), Msg::Increment);
        assert_eq!(model.count, 1);
    }
}

    Where messages come from¶

    For the counter, every change begins with a tap. Other screens can change while the user’s hands are off the phone. Gallery also needs to know when the OS finishes a clipboard request and when the user presses Back. It implements DeclarativeApp and registers an AppAdapter::new(app) in its native factory. The adapter keeps a MountedView for that app instance and dispatches each input once.

    Input Where it goes
    A press on a button with .on_press(Msg::Save) The adapter resolves the binding and calls the app’s update(Msg::Save).
    A quote from Live monitor’s worker The worker queues a typed message through AppSender. Erosion wakes the UI loop and calls the app’s update method.
    System Back or a clipboard result The app’s on_host_event receives the unbound HostEvent. The app can pop a page or match a result to a pending request.

    To follow a message that starts outside the UI, open the Live monitor walkthrough. It covers what happens when a worker finishes after the user has left the screen.

    An app can also supply a snapshot, request clock ticks, or keep the screen awake during a match. These hooks have defaults, so a new feature only needs the ones it uses. The underlying runtime::Application trait is available if you want to implement dispatch and rendering yourself.

    Gallery uses toggle(...).on_toggle(Msg::Toggle), slider(...).on_slide(Msg::Slide), and choice_list(...).on_pick(Msg::Pick). Their messages carry a Boolean, a u16 value, and a stable u32 item ID respectively. Both field and date deliver strings through on_input. Apply an app-selected palette with strata_screen(title).theme(theme).

    How the games use it¶

    • Falling Blocks binds the Left button to Msg::Move(Move::Left). A left swipe is classified as Move::Left and reaches the same Game::apply_move rule. The game owns its board, score, and phase. The application adapter handles clock ticks, navigation, and saving the high score. Start with samples/falling-blocks/src/view.rs and follow the binding into src/lib.rs.
    • Field Catch binds both keyboard submission and the Join Field button to Msg::JoinField. Its reducer takes an AppInput, which can carry a UI message, a typed WebRTC callback, or another platform event. It returns the next model and effects for the host to execute, such as requesting GPS. Start with samples/field-catch/src/view.rs and follow AppInput and update in src/lib.rs. Navigation and effects

    Compose the view¶

    A child block accepts immutable let bindings, if let, if/else, match with braced arms, and for. End leaf and component expressions with a semicolon. Return a ViewNode<Msg> for one control or a Fragment<Msg> for several siblings. A fragment adds no native container. Use item-derived keys in loops and give every interactive source a unique key across the whole screen, including toolbar and accessibility actions.

    Place header actions in the screen’s toolbar { ... } block. Field Catch enables its video call button when a call is available. The label, availability, and message sit together in the view:

    toolbar_item("video-call", "Video call", "video_camera")
    .enabled(can_call)
    .on_press(Msg::VideoCall);

    How a control becomes a native view¶

    A Control describes what to render. For a map, that includes pins and overlays. A pin can have a glyph, and a circle overlay carries its center, color, and radius in metres. For a button, the control holds its label and optional icon.

    A Node places one control in the screen tree and gives it a stable key, styling, and accessibility information. A typed builder such as button(...) lets you bind a Rust message alongside that node. Erosion keeps the binding in Rust and sends the screen description to the phone. When the phone reports a press, the adapter uses the key to find the message.

    For a drawing surface, start with canvas(key, width, height), supply the shapes, and bind pointer input with .on_pointer(...). For a map, bind .on_map_idle(...) to remember its viewport or .on_map_heading(...) to follow rotation. Field Catch uses the heading to keep its aiming puck aligned with the map.

    Keep an editor focused¶

    Give an editable field a key that stays the same as its text changes. The native editor can then keep its focus and selection when Rust renders again. Bind the edit next to the field:

    field("title", "Note title", &model.title).on_input(Msg::TitleChanged);
button("save", "Save note").on_press(Msg::Save);

    Here Msg::TitleChanged(String) carries the new text into the app. A keyboard submit can send the same Msg::Save as the button. For a list, give each item a persistent ID and use .on_pick(...) to receive it. That way the same item opens after the user sorts or filters the list.

    Choose an authoring style¶

    Widget functions and chainable modifiers cover common controls. Use Control variants directly for more specialized declarations. The optional ui! macro constructs the same keyed nodes:

    use erosion_ui::{ui, widgets::button};
let form = ui!("form" => Column [
    ui!("volume" => Slider { label: "Volume".into(), value: 35 }),
    button("save", "Save"),
]);

    The engine compares successive screen descriptions and sends changes over a revisioned bridge. The declarative API, individual widget constructors and both macros use that update path.

    Draw a custom shape¶

    Build a CanvasPath in the canvas's logical coordinates and put the resulting Draw in the shapes list of Control::Canvas. This leaf has a cubic curve on one side and a quadratic curve on the other.

    use erosion_ui::design::CanvasPath;

let leaf = CanvasPath::new(10., 50.)
    .cubic_to(10., 20., 40., 10., 70., 10.)
    .quad_to(65., 50., 10., 50.)
    .close();
let shapes = vec![
    leaf.clone().fill("#568865"),
    leaf.stroke("#294B35", 2.),
];

    Curve arguments give the control points first and the endpoint last. Use line_to for straight edges and move_to for another contour. Fills use the nonzero winding rule, so an inner contour drawn in the opposite direction makes a hole. Shapes paint in list order. Stroke widths use canvas units.

    App-owned native surfaces¶

    Field Catch projects its Rust match into a serializable AR scene. It emits a Control::NativeSurface with the renderer name catch-field, a key for the mounted instance, and its scene as JSON properties. The native host creates the view and delivers updated properties on each render. Field Catch implements the renderer in its Android activity and its iOS scene extension. The game owns camera sharing, the ball trajectory, and cleanup when the surface leaves the window.

    Where a new feature belongs¶

    A new game move, editing command, or validation rule can live entirely in your app’s Rust code. Field Catch adds its own network messages this way. Its map and AR views both read the same match, so switching views preserves the flight in progress.

    For an OS feature, first look for an existing device operation. To expose a new capability to every Erosion app, define its request and result in the framework and implement it in the native hosts. For a renderer specific to one app, Field Catch’s AR surface shows how to keep the native implementation alongside the game.
